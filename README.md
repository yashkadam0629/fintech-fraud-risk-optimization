# Fintech Fraud Detection & Customer Friction Optimization Framework

An end-to-end analytics system that treats fraud prevention as a cost-minimisation
problem rather than a classification problem.

> **No performance number is written by hand anywhere in this repository.**
> Every figure in `reports/` is generated by `run_pipeline.py` from your own run.
> Until you run it, those files do not exist. That is deliberate.

---

## 1. Project overview

A fraud control is never free. Every transaction blocked to stop a fraudster
might be a real customer buying groceries. Block too little and the company
absorbs fraud losses. Block too much and it pays in support calls, abandoned
payments and churn.

Most fraud projects stop at "here is a classifier with a good AUC". This one
continues to the question the business actually has to answer:

> At what probability should we intervene on a transaction, given explicit
> assumptions about what a missed fraud and an annoyed customer each cost?

The output is an intervention policy with a defensible threshold, a sensitivity
map showing how that threshold moves with the economics, and a three-page
operational dashboard.

## 2. Business problem

|  | Threshold too low (intervene often) | Threshold too high (intervene rarely) |
| --- | --- | --- |
| Fraud losses | Low | High |
| Customer friction | High | Low |
| Review capacity needed | High | Low |

The cost-minimising point lies between them, and it **moves** when the cost
assumptions move. Locating it, and showing how far it travels, is the project.

## 3. Dataset

PaySim1 synthetic mobile-money transactions (Kaggle: `ealaxi/paysim1`).
Approximately 6.36 million rows, 11 columns, a 30-day simulated month, one
binary fraud label. Download instructions, full schema and licence:
[`data/README.md`](data/README.md).

## 4. Dataset limitations that shaped every design decision

These are not disclaimers bolted on at the end. Each one changed what got built.

| Limitation | Consequence for the build |
| --- | --- |
| `step` is an hourly index, not a timestamp | No 10-minute or minute-level velocity exists. Windows are 24h, 72h, 168h, implemented with SQL `RANGE` over `step`. |
| No geography, device, IP or merchant category | No location, impossible-travel or device features. Behavioural signal comes from counterparty structure instead. |
| The dataset spans only ~30 days | No true 30-day rolling baseline for early transactions. An expanding past-only baseline is used, and its coverage is measured and published. |
| Originating accounts rarely repeat | Per-customer baselines are undefined for most rows. Measured in Stage 1, which then shifts the feature design to the destination side. |
| Balance fields have simulator-specific transaction/reversal mechanics | The primary model excludes balance fields conservatively and focuses on behavioural and counterparty signals. `newbalance*` fields are post-transaction; `oldbalance*` fields are pre-transaction but are excluded from the primary model and discussed separately in the leakage audit. |
| No cost, chargeback or recovery data | Every monetary figure in this project is a stated assumption, labelled SIMULATED. |

## 5. Data leakage discussion

PaySim provides four balance fields around each transaction: `oldbalanceOrg`
and `oldbalanceDest` represent balances before the transaction, while
`newbalanceOrig` and `newbalanceDest` represent balances after the
transaction. The primary model excludes all balance fields as a conservative
design choice because the simulator's balance and reversal mechanics can create
signals that are difficult to interpret as clean authorization-time behavioural
evidence. In particular, the `newbalance*` fields are post-transaction values
and would not be available when an authorization decision is being made.
The `oldbalance*` fields are pre-transaction values and may be usable in a
different model, so they are treated separately rather than being described
as inherently fraudulent-label leakage.

`isFlaggedFraud` is excluded for a different reason: it is a control output
rather than an observation, and in PaySim it is set only on transactions the
simulator already treats as fraudulent. It is target-derived. It is kept as a
benchmark baseline, never as a feature.

Stage 1 measures the separation rather than asserting it, and produces a
decision table (`column | leakage risk | reason | decision`). The pipeline also
trains an optional **leakage demonstration model** on the excluded columns, so
the size of the illusion is quantified rather than described. That model is
labelled `LEAKAGE DEMONSTRATION - NOT VALID FOR DEPLOYMENT` everywhere it
appears and is never used for any decision.

## 7. SQL analytics

`sql/03_behavioral_features.sql` is the feature layer, built with CTEs and
window functions. The distinction it is careful about:

```sql
-- ROWS: the previous 24 ROWS for this account, however far apart in time.
COUNT(*) OVER (PARTITION BY name_dest ORDER BY step
               ROWS  BETWEEN 24 PRECEDING AND 1 PRECEDING)

-- RANGE: every row whose step falls in [step-24, step-1].
-- One step is one hour, so this genuinely means "the last 24 hours".
COUNT(*) OVER (PARTITION BY name_dest ORDER BY step
               RANGE BETWEEN 24 PRECEDING AND 1 PRECEDING)
```

Velocity is a time concept, so velocity uses `RANGE`. Lifetime history is a
sequence concept, so it uses `ROWS UNBOUNDED PRECEDING`. **Every frame ends at
`1 PRECEDING`, never `CURRENT ROW`**, which is what keeps the features
computable at authorisation time.

Feature families, all past-only:

- **Velocity** - destination transactions in the previous 24h / 72h / 168h, same-hour concurrency, 24h-versus-168h acceleration
- **Destination behaviour** - prior transaction count, prior average and maximum amount, gap since last transaction, first-ever-seen flag
- **Counterparty fan-in** - distinct senders seen so far, computed without `COUNT(DISTINCT)` in a window (PostgreSQL does not allow it) by marking first contacts and taking a past-only running total
- **Relationship** - prior transactions between this exact sender and receiver, new-relationship flag, prior value transferred
- **Origin behaviour** - the same expanding aggregates for senders, published *with their coverage percentage* rather than presented as fully populated
- **Amount context** - log amount, round-number flag, amount relative to the transaction type's own past average
- **Time** - hour within the 24-hour cycle (`step` itself is excluded: it encodes position in the simulation and does not generalise forward)

`src/feature_engineering.py` mirrors the SQL for the Python pipeline. Running
both and comparing is a real correctness check.

## 8. Machine learning

- **Time-aware split** on `step`: earliest 60% train, next 20% validation, final 20% test, with no step spanning two sets. A random split would let the model see later transactions from a destination account during training and earlier ones at test time. Every behavioural feature here is cumulative, so that inflates results and says nothing about tomorrow.
- **Models**: logistic regression (scaled) and random forest, plus XGBoost when installed. Two core models, not twelve. The project is about the decision layer, not algorithm shopping.
- **Class imbalance is handled at the decision layer, not by reweighting.** `class_weight="balanced"` inflates predicted probabilities, which destroys the calibration the cost model depends on and pushes every cost-optimal threshold against 0.99. Pass `--class-weight balanced` to see it happen.
- **Selection metric: PR-AUC on validation.** ROC-AUC's false-positive rate has the enormous legitimate population in its denominator, so it stays flattering while precision is poor. PR-AUC's no-skill baseline is the fraud rate itself, which makes improvement legible.
- The test period is scored once, at the end.

## 9. Model evaluation

Reported: precision, recall, F1, ROC-AUC, PR-AUC, confusion matrix, fraud
capture rate, false-positive rate, alert volume, and top-K capture (what share
of fraud lands in the queue if the team can only review the top 0.1% / 1% / 5%
of scores). The Stage 1 baselines define the floor: any model that cannot beat
"flag every TRANSFER and CASH_OUT" has not earned its complexity.

## 10. Financial optimization

```
TOTAL COST(t) = FN(t) x C_fn  +  FP(t) x C_fp

C_fn = $500   cost of one missed fraudulent transaction    (SIMULATED)
C_fp = $25    cost of one blocked legitimate transaction   (SIMULATED)
```

Thresholds are swept from 0.01 to 0.99. The sweep also evaluates thresholds at
quantiles of the score distribution, because a calibrated model puts almost all
of its mass below 0.05 and a fixed 0.01 grid would collapse the interesting
region into four points. Both sets appear in the output, tagged in a
`grid_source` column.

**The threshold is chosen on the validation period and reported on the test
period.** Optimising a threshold on the same data you then quote is a subtler
version of the leakage this whole project is about.

Risk bands are derived, not invented. Two interventions have two costs: a
step-up verification ($5 assumed) annoys a customer less than a hard decline
($25 assumed), so it pays for itself at a lower level of suspicion. Running the
cost model twice produces two thresholds, and MEDIUM is exactly the region
between them.

| Band | Action | Derivation |
| --- | --- | --- |
| LOW | allow | below the verification threshold, intervention costs more than it saves |
| MEDIUM | step-up verification / manual review | worth intervening at verification cost, not at blocking cost |
| HIGH | block | expected fraud loss exceeds the full blocking cost |

## 11. Cost sensitivity analysis

25 scenarios: missed-fraud cost in {100, 250, 500, 750, 1000}, false-positive
cost in {5, 10, 25, 50, 100}. For each, the minimum-cost threshold, resulting
capture rate, false positives and total cost. Output as a table and two
heatmaps. The point of the section is that two teams running the identical
model can both be right to operate at very different thresholds, because
disagreement about aggressiveness is usually disagreement about costs.

## 12. Dashboard

Three Power BI pages fed by `outputs/dashboard_data/`. Layout and DAX notes:
[`dashboard/README.md`](dashboard/README.md).

1. **Executive risk overview** - KPI cards, fraud trend, fraud by type, threshold-versus-cost curve, capture-versus-friction trade-off
2. **Fraud operations** - action queue sorted by fraud probability, with risk band, velocity and counterparty context per alert
3. **Customer friction** - false positives by type, amount band and time, with simulated friction cost attached

## 14. Business insights

Filled in from your run; see `reports/findings.md`. The structural findings
that hold regardless of the exact numbers:

1. Accuracy is unusable as a fraud metric at this base rate.
2. Balance fields are excluded from the primary model because of
PaySim's simulator-specific balance/reversal mechanics and the need to keep
the authorization-time feature set conservative.
3. Sender history barely exists in this dataset, so counterparty behaviour carries the behavioural signal.
4. The intervention threshold is a pricing decision, not a model property.
5. Customer friction is concentrated, so it can be targeted with a softer control rather than accepted as a cost of doing business.

## 15. Limitations

Synthetic data; no geography, device or IP signal; hourly resolution only;
simulated cost assumptions with no chargeback or recovery data behind them;
uniform false-positive cost when real friction varies by customer and
transaction; uncalibrated tree probabilities, so threshold values are not
directly comparable across models; a single held-out period rather than rolling
revalidation; no confidence intervals.

**Nothing in this repository is a realised saving for any company.**

## 16. Future improvements

Real-time scoring, streaming feature computation, device fingerprinting, IP
intelligence, merchant risk scoring, graph-based detection over the
sender-receiver network, adaptive thresholds driven by live cost telemetry,
chargeback-derived cost inputs, investigation feedback loops, model monitoring
with drift detection, human-in-the-loop review, formal model governance. None
of these is implemented here.

## 17. Installation

```bash
git clone <your-repo-url>
cd fintech-fraud-optimization

python -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt
```

Download the dataset from https://www.kaggle.com/datasets/ealaxi/paysim1,
unzip it, and put the CSV in `data/raw/`. The loader auto-detects any CSV
there whose header matches the PaySim schema.

## 18. Usage

```bash
# everything, stages 1 through 5
python run_pipeline.py

# quicker first pass: lighter model settings
python run_pipeline.py --fast

# development run on an early time window
python run_pipeline.py --nrows 1000000 --fast

# compare what class re-weighting does to the thresholds
python run_pipeline.py --class-weight balanced
```

Expect roughly 10 to 30 minutes on the full dataset depending on your machine,
and about 3 GB of RAM at peak. Use `--fast` or `--nrows` if that is tight.

No dataset yet? Verify the plumbing on synthetic data:

```bash
python tests/make_sample_data.py --rows 150000
python run_pipeline.py --csv data/raw/sample_paysim.csv --fast
```

Those numbers are invented and must never be quoted as findings.

The SQL layer runs independently:

```bash
createdb fraud_analytics
psql -d fraud_analytics -f sql/01_schema.sql
# then \copy the CSV in, as documented at the top of that file
psql -d fraud_analytics -f sql/02_data_validation.sql
psql -d fraud_analytics -f sql/03_behavioral_features.sql
psql -d fraud_analytics -f sql/04_analysis_queries.sql
```
